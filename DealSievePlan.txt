DealSieve

Persistent Opportunity Intelligence for Commercial Real Estate

One-line pitch

DealSieve is a persistent acquisition agent that rejects opportunities, remembers exactly why they failed, watches the conditions that could change that decision, and interrupts the investor only when a deal becomes investable.

The product is not an AI underwriting assistant.

Underwriting is one internal capability.

The product is an agent that maintains opinions about opportunities over time.

---

1. Core insight

Most acquisition software assumes:

Find deal
→ analyze deal
→ decide
→ forget/reject

DealSieve assumes:

Encounter opportunity
→ form an evidence-backed opinion
→ reject if appropriate
→ remember why
→ calculate what would change the decision
→ watch relevant conditions
→ re-evaluate automatically
→ interrupt human only if decision changes

The central product principle is:

«The best acquisition agent should not help professionals examine more opportunities. It should help them examine fewer.»

The second core insight is:

«A rejected opportunity is not necessarily a dead opportunity.»

A property rejected at $1.55M may be attractive at $1.27M.

DealSieve therefore stores not only:

«NO»

but:

«NO because X, and the answer becomes YES if Y changes.»

---

2. What makes this different

Do not position the product as:

- AI reads Offering Memorandums
- AI extracts rent rolls
- AI calculates cap rates
- AI summarizes CRE listings
- AI underwriting copilot

Those categories are increasingly commoditized.

Position it as:

«Persistent opportunity monitoring with counterfactual decision thresholds.»

Its distinctive behavior is:

Broker email arrives
      ↓
DealSieve rejects deal
      ↓
Computes exact viability frontier
      ↓
Remembers opportunity
      ↓
Conditions change weeks/months later
      ↓
DealSieve recognizes same opportunity
      ↓
Re-evaluates automatically
      ↓
Decision flips
      ↓
Human gets interrupted

That lifecycle is the product.

6. State model

Use four meaningful economic states.

NEW
 ↓
SCREENING
 ↓

┌───────────┬────────────┬───────────────┐
│           │            │               │
DEAD        WATCH        NEAR           REVIEW

DEAD

The opportunity has a structural problem.

Examples:

- unacceptable environmental exposure;
- incompatible zoning;
- catastrophic physical issue;
- unacceptable tenant concentration;
- title/easement problem;
- functionally obsolete configuration.

A normal price reduction does not resolve the core problem.

Do not continuously monitor DEAD deals.

---

WATCH

Economically unacceptable today, but potentially investable.

Examples:

- overpriced;
- insufficient DSCR;
- financing too expensive;
- NOI too low;
- seller terms unattractive.

Store a viability frontier.

---

NEAR

Within configurable distance of passing.

Initial definition:

≤5% change in purchase price

Architecture should eventually support distance based on financing/NOI as well.

NEAR deals may deserve somewhat more frequent monitoring.

---

REVIEW

Passes all immutable hard gates.

Human attention is now justified.

This is not equivalent to:

BUY

DealSieve never autonomously recommends irreversible capital deployment.

7. Viability frontier

This becomes a first-class domain concept.

Every WATCH opportunity should answer:

Why did this fail?

What is preventing it from passing?

What specific change would make it pass?

Example:

{
  "current_price": 1550000,
  "max_viable_price": 1270000,
  "distance_pct": 0.1806,

  "binding_constraints": [
    "normalized_cap_rate",
    "dscr"
  ],

  "possible_paths_to_viability": [
    {
      "variable": "purchase_price",
      "required_value": 1270000
    }
  ]
}

For the hackathon implement:

purchase-price frontier only.

Design the domain model so future versions can solve for:

- required NOI;
- required rent;
- maximum interest rate;
- required seller-financing terms;
- occupancy improvement;
- equity contribution.

13. Acquisition Agent

Responsibilities:

- understand incoming email/message;
- identify property;
- find existing opportunity;
- extract new information;
- reconcile contradictions;
- determine what changed;
- invoke deterministic tools;
- update opportunity state;
- decide whether a human interruption is warranted.

It may not:

- override policy;
- invent missing financial inputs;
- change deterministic calculations;
- send an outbound email without approval.

---

14. Skeptic Agent

Runs only when an opportunity enters REVIEW.

Prompt philosophy:

«Assume the preliminary economics look attractive. Your job is to identify reasons the investor should still refuse to proceed.»

Focus on:

- unsupported assumptions;
- lease rollover;
- tenant concentration;
- environmental risk;
- physical condition;
- roof/HVAC/paving;
- access/easements;
- zoning;
- seller-related tenants;
- suspiciously low expenses;
- broker claims lacking evidence;
- financing risk.

Output:

Verified concerns

Unverified concerns

Required broker questions

Recommended professional diligence

Potential structural deal killers

Never recalculate finance independently.

18. Price viability solver

Given normalized NOI and financing assumptions, calculate the highest purchase price at which all hard constraints pass.

Pseudo:

def solve_max_viable_price(deal, policy):

    low = 0
    high = deal.asking_price

    while high - low > 1000:

        candidate_price = (low + high) / 2

        result = underwrite(
            deal,
            purchase_price=candidate_price,
            policy=policy,
        )

        if result.passes:
            low = candidate_price
        else:
            high = candidate_price

    return low

Return:

maximum viable purchase price
binding constraints
distance from asking

This solver should have excellent test coverage.

Proxy:

1. receives request;
2. serializes context;
3. invokes configured CLI;
4. captures stdout;
5. validates structured output where expected;
6. converts result back into OpenAI-compatible response.

Use this for:

- concise escalation text.

40. Coding-agent instructions

Codex/Claude Code should follow these operating rules.

1. Work autonomously.
2. Do not repeatedly ask for implementation preferences where a reasonable default exists.
3. Optimize for a reliable hackathon demo, not production architecture.
4. Preserve the distinction between:
   - probabilistic extraction/reasoning;
   - deterministic finance;
   - immutable policy;
   - human irreversible decisions.
5. Never weaken investment thresholds to make a fixture pass.
6. Do not allow an LLM to produce authoritative financial arithmetic.
7. Maintain immutable event and underwriting history.
8. Treat WATCH → changed condition → REVIEW as the highest-priority end-to-end path.
9. Default model development to local CLI proxies.
10. Keep AWS provider logic behind abstractions.
11. Never place credentials in code.
12. Write tests before optional features.
13. Keep "STATUS.md" current.
14. Commit at coherent milestones.
15. If an optional feature jeopardizes the core workflow, cut it.
16. Ensure the entire demo is runnable offline/local except model CLI access.
17. A deal producing no human interruption is a successful output.
18. Zero qualifying properties is a legitimate system result.
19. Preserve evidence provenance.
20. Never silently resolve contradictory source information without recording the conflict.

Final product statement

DealSieve is not an AI that reads real-estate documents.

It is an agent that develops and maintains an opinion about every acquisition opportunity it encounters.

It can say:

«Not now.»

It knows:

«Why not.»

It calculates:

«What would change my mind.»

And it watches quietly until that happens.

Only then does it ask for a human's attention.
